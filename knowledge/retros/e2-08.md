# E2-08 validation — HR policy admin with effective dating

## Result

- **Schema:** `db/migrations/0004_policy_effective_dating.sql` makes `leave_policies`
  effective-dated.
  - Adds `effective_from date`, backfills existing rows to `date '2000-01-01'` (they predate
    effective dating and apply to every period), then `NOT NULL` + a month-start CHECK.
  - Replaces `unique (user_id, leave_type_id)` with
    `unique (user_id, leave_type_id, effective_from)`.
  - Grants `INSERT, UPDATE` on `leave_policies` to `leavetrack_app`; `DELETE` stays ungranted.
  - Adds `policy_audit_log` (employee, leave type, effective month, previous rate, new rate,
    actor, timestamp) with RLS, the `leavetrack_app` allow policy, the `AS RESTRICTIVE`
    `anon, authenticated` deny policy, `SELECT/INSERT` only, and the existing append-only
    triggers. This follows ADR-LeaveTrack-E005 for every new table.
- **Why a new log:** `audit_log` is request-bound (`leave_request_id NOT NULL`) and its action
  CHECK is `('submitted','approved','rejected')`. Policy events have no request, so they get
  their own append-only table. The request trail is untouched.
- **Seed:** `db/seed.sql` writes `effective_from = date '2000-01-01'` and conflicts on the new
  3-column key; still idempotent.
- **Reads resolve the rate by date** (`knowledge/patterns/effective-dated-policy.md`):
  - `runAccrual(period)` uses the **run period** (`distinct on … effective_from <= period`).
  - `getBalancesForUser` uses a `left join lateral … effective_from <= current UTC date`.
  - `listPolicyOverview` uses the same current-UTC-date predicate, so a future-dated row is not
    shown before its month.
- **Writes:** `lib/db/policies.ts` `upsertPolicyRate` runs one transaction:
  - rejects a month before the current UTC month (400);
  - reads the same-month row and the prior effective row, so `previous_rate` is the rate in
    effect immediately before the new month;
  - returns `auditWritten: false` for a same-month/same-rate save and writes nothing;
  - rejects a month whose `(user, leave type, period)` is already in `accrual_ledger` (409): the
    idempotent run would never apply the change, so it is refused instead of confirmed;
  - otherwise upserts one dated row and inserts exactly one `policy_audit_log` row;
  - unknown employee 404, untracked leave type 400.
- **API:** `POST /api/policies` (`withApiHandler`): 401 no session, 403 employee/manager, 400
  malformed JSON or invalid/mis-dated input, 409 for a month that has already accrued, 200 with
  `PolicyRateResult`. The actor comes from the session; `policyRateInputSchema` is strict, so a
  client-supplied actor is 400.
- **UI:** `/settings/policies` is read/write for HR (`canConfigurePolicies`): a create/correct
  form, the current-rate snapshot grouped by leave type, the recent change log, accrual status,
  and the guardrails. The form defaults to next month, rejects past months client-side, and
  distinguishes "Policy rate saved" from "No change to save". Every page is now DB-backed; no
  application page imports `lib/mock/data.ts`.
- **Docs:** `AGENTS.md`, `README.md`, `ARCH-LeaveTrack-v1.0.md`,
  `knowledge/rules/arch-summary.md`, `knowledge/patterns/effective-dated-policy.md`,
  `knowledge/patterns/accrual-idempotency.md`, and
  `docs/arch-docs/ADR-LeaveTrack-E006-Policy-Effective-Dating.md`. `ADR-LeaveTrack-E002`
  (user-owned) was not modified.

## Acceptance criteria

- **HR can create and update policies — PASS.** `POST /api/policies` + the `/settings/policies`
  form create a dated row for a new month and correct the current/future month's row.
  `policy-admin.integration.test.ts` asserts create → change → same-rate no-op.
- **Employees and managers receive 403 — PASS.** `policy-route.test.ts` asserts 403 for both
  roles with the standard error envelope and no DB write; no session is 401.
- **A mid-year rate change affects only future periods — PASS.** The accrual test proves the old
  rate is used before the change and the new rate at/after it; balances already accrued are never
  recalculated.
- **Accrual resolves the policy effective for the run period — PASS.** `runAccrual` filters
  `effective_from <= $period`, not today. The test's far-future period would fail if it resolved
  against today.
- **One audit row per change — PASS.** A create writes one row (`previous_rate` = prior rate), a
  change writes one (`old → new`), and a same-month/same-rate save writes none.

## Validation findings

- [FIX NOW — fixed] A rate saved for the current month was accepted and confirmed by the UI even
  when that month had already accrued; `accrual_ledger` is the idempotency marker, so the change
  could never apply. `upsertPolicyRate` now rejects an already-accrued period with 409 inside the
  same transaction, the form and page copy state the lock, and `policy-admin.integration.test.ts`
  proves the rejection leaves `leave_policies` untouched.
- [FIX NOW — fixed] `ADR-LeaveTrack-E005` still listed `leave_policies` as `SELECT` only
  ("admin writes are future server work") and did not mention `policy_audit_log`, so the grant
  matrix contradicted the shipped migration. Amended the matrix and added an explicit
  "Amended by E2-08" note instead of rewriting the historical decision.
- [FIX NOW — fixed] `knowledge/rules/arch-summary.md` had a duplicated `## Data Model` heading
  (pre-existing, not introduced by E2-08); removed the duplicate while editing the same file.
- [BACKLOG] The current-rate snapshot groups by leave type and shows `max()` of the per-employee
  rates, so mixed rates display as the highest one with no "varies" hint. The change log and the
  per-employee form remain correct; a spread/breakdown belongs in a follow-up.
- [BACKLOG] The form's `step="0.25"` is a spin-button hint while the schema accepts any two
  decimals; align the step or state the granularity once a rate needs thirds of a day.
- [BACKLOG] `POST /api/policies` has no handler test for the DB-layer 404 (unknown employee) and
  past-month 400; E2-15 owns the full route matrix.
