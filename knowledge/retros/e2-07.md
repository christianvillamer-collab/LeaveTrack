# E2-07 validation — HR cross-team override view

## Result

- `lib/auth/policy.ts` gained two predicates without touching the manager gates:
  - `canOverrideRequests(subject)` — HR-only role gate for `POST /api/leave-requests/:id/override`.
  - `canOverrideRequest(actor, scope)` — record gate: HR, `pending`, and never the actor's own request.
  - `canViewRequest`, `canDecideRequest`, `canViewTeam`, `canDecideTeamRequests`, and
    `canManageRequests` are unchanged. HR still cannot use `scope=team` or the decision endpoint.
- `lib/validation/leave.ts` has `overrideInputSchema` (strict): `override: z.literal(true)`, a
  `decision` enum, and a trimmed 3–2000 character `reason`. Missing/false flags and extra fields are
  400s at the boundary. `decisionInputSchema` is untouched.
- `lib/db/leave.ts`:
  - `decideLeaveRequest` and `overrideLeaveRequest` share one private `applyDecision` transaction:
    row lock → relationship gate → pending/duplicate 409 → balance guard 409 → status update →
    append-only audit insert. Balance and audit semantics cannot drift between modes.
  - `overrideLeaveRequest` rejects the actor's own request (403), requires a non-blank reason,
    writes `decided_by` as the HR actor, stores the reason in `decision_note`, and writes
    `action = approved|rejected` with detail `HR override — approved by <name>: <reason>. …` or
    `HR override — rejected by <name>: <reason>. …`.
  - `listOrgLeaveRequests()` is a separate no-manager-filter query for the HR queue.
    `listTeamLeaveRequests()` keeps `e.manager_id = ${managerId}` byte-for-byte; the shared
    `toTeamLeaveRequest` mapper only removed duplicated row mapping.
- `app/api/leave-requests/[id]/override/route.ts` (new) mirrors the decision route:
  `withApiHandler`, session 401, `canOverrideRequests` 403, UUID 404, JSON 400, schema 400.
- UI:
  - `TeamDecisionActions` has an `override` mode that posts `{ override: true, decision, reason }`
    to `/override`, requires a reason for approvals too, changes the dialog copy, and warns that the
    action bypasses the manager chain and is audited. Manager mode is unchanged.
  - `TeamRequestTable` forwards `override`.
  - `/approvals` renders the HR org-wide queue with override buttons, org stats, and an aside that
    states the manager predicate is unchanged. Manager branch and `getTeamLeaveData` are untouched.
  - `/requests/[id]` shows an HR override panel for pending, non-self requests.
  - The HR dashboard card links to the override queue.
- No schema or migration change. `audit_log.action` stays `('submitted','approved','rejected')`;
  override provenance lives in `decided_by` plus the `HR override` detail prefix.

## Acceptance criteria

- **HR can view any request — PASS.** `canViewRequest` already allowed HR; `listOrgLeaveRequests`
  and the `/approvals` HR branch now surface the org queue, and the detail page renders for HR.
- **Employees and managers cannot widen their view — PASS.** Employee `/approvals` redirects to
  `/forbidden`; manager detail of another team's request redirects to `/forbidden`; HR still fails
  `canViewTeam`/`canDecideTeamRequests`.
- **Manager scope predicate unchanged — PASS.** `listTeamLeaveRequests` still filters
  `e.manager_id = ${managerId}` in SQL; no manager branch of `/approvals` changed.
- **Override requires an explicit flag and reason — PASS.** `overrideInputSchema` is strict with
  `z.literal(true)` and a required 3–2000 character reason; the UI sends the flag and enforces the
  reason before the request.
- **Audit rows are written — PASS.** The shared transaction inserts one `approved`/`rejected` row
  with the HR actor and an `HR override — <decision> by …` detail containing the reason and any
  balance delta. Integration test asserts the actor, action, detail (including the `HR override`
  prefix), and no second row on duplicate.

## Accepted deferrals (not blockers)

## Validation issues

- [FIX NOW — fixed] `/approvals` rendered override buttons on HR's own pending request; the server
  403s, so the UI offered an action that always fails. `TeamRequestTable` now takes a `canActOn`
  predicate, and the HR queue passes `canOverrideRequest`, matching `/requests/[id]`, with the
  server 403 as the backstop.
- [FIX NOW — fixed] The audit detail read `Approved by HR override — …` while the docs and the
  E2-11 backlog promised a detail prefixed `HR override`. The row now starts
  `HR override — approved by …` / `HR override — rejected by …`, and the integration test asserts
  the prefix instead of a loose `toContain`.
- [FIX NOW — fixed] The over-balance 409 message and README said "HR override is required", but in
  E2-07 the HR override returns the same 409 (over-balance is E2-11). Both now state that the
  request cannot be approved until the balance path lands, so the UI no longer sends HR down a
  dead end.
- [BACKLOG] On `/requests/[id]`, HR's "Back" link still points at `/audit` even when the panel was
  reached from `/approvals`. Point it at `/approvals` once the HR queue becomes the primary entry.
- [BACKLOG] No other issues; all five acceptance criteria pass.
