# E2-05 validation — DB-backed request list and detail

## Result

- `/requests` reads `listScopedLeaveRequests`: employee = own rows, manager = own + direct reports
  (`e.manager_id = :current_user_id` as a SQL predicate), HR = every active request.
- `/requests/[id]` reads `getLeaveRequestDetail` and `listAuditEventsForRequest`; the audit trail is
  chronological (oldest first) and scoped to the one request.
- Both routes import no `lib/mock/data`; the dashboard fixture surface is untouched for E2-06.
- The detail page authorizes in `generateMetadata` before exposing employee/leave data, and returns a
  generic title for missing, unauthorized, or DB-unavailable records.
- Invalid non-UUID path ids 404 through `leaveRequestIdSchema` instead of reaching Postgres.
- Cross-team access redirects to `/forbidden` through `canViewRequest`; the list itself never returns
  another team's rows.
- The demo `ApprovalCard` is replaced by the real `TeamDecisionActions` on the detail page; the
  decision endpoint, balance deduction, and audit write already existed.
- `RequestTable` now accepts `RequestSummary`, which is structurally satisfied by the fixture
  `LeaveRequest[]`, so the dashboard keeps its existing prop shape.
- DB integration coverage: `tests/leave-request-detail.integration.test.ts` (7 cases: employee scope,
  manager scope, HR scope, detail shape, unknown id, soft-delete hiding, per-request audit order).
  Registered in `npm run test:db`.
- Full gate passed: format, lint, typecheck, unit (83 passed / 31 skipped), DB integration
  (all 8 files, 31 tests), and production build.

## Acceptance criteria

- Newly submitted request appears in list and detail — PASS. Signed in as Maya, submitted an Unpaid
  request through `POST /api/leave-requests`, then found the new id in `/requests` and read its
  reason and `submitted` audit event on `/requests/[id]`.
- Detail shows the audit trail — PASS. The submitted event renders in the trail for the employee and
  for the manager reading a direct report's request.
- Cross-team access returns 403/404 — PASS. A manager opening another manager's report and an
  employee opening a colleague's request both land on the `/forbidden` 403 surface; unknown or
  malformed ids 404.
- No `lib/mock/data` import in these routes — PASS (grep and runtime).
- 375px layout is clean — PASS. `/requests` and `/requests/[id]` had
  `scrollWidth === clientWidth` and no out-of-viewport elements at 375 and 320 for employee, manager,
  and HR sessions. The list content checks also ran at 1440.

Runtime checks used a temporary headless-Chrome CDP script outside the repo against `next start`;
the submitted validation record was soft-deleted afterwards.

## Accepted deferrals (not blockers)

- Dashboard still reads `lib/mock/data.ts`; E2-06 moves it to DB queries.
- Pagination/filtering on `/requests` remains E2-13.
- HR cross-team override and request-detail HR actions remain E2-07 / ADR-E004.
- DB-down on these routes shows the established `DATABASE_NOT_CONFIGURED` alert; retryable error
  states and loading skeletons remain E2-18.
- `requestById()` in `lib/mock/data.ts` now has no consumers but stays until E2-06 deletes the
  fixture surface in one change.
