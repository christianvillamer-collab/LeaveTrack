## Acceptance criteria

- **ADR records the choice — PASS.** `ADR-LeaveTrack-E005` (Accepted) records four options
  (RLS only, role only, both, `FORCE RLS`), the chosen two-layer design, the grant matrix, the
  anon-key analysis, the cutover runbook, rollback, and consequences. Linked from
  `ARCH-LeaveTrack-v1.0.md` (Security + ADRs).
- **Every table has an explicit grant/deny policy — PASS.** All seven E2-04 tables have RLS
  enabled, a `<table>_app_access` policy for `leavetrack_app`, and a `<table>_deny_clients` policy
  for `anon, authenticated` (`using (false) with check (false)`). Explicit grants per table are in
  the migration, and `schema_migrations` is revoked from the client roles.
- **No anon-key path bypasses authorization — PASS (after deployment).** `anon`/`authenticated`
  hold zero table privileges on all seven tables and `schema_migrations`; default table/sequence
  privileges are revoked for future objects. The only `public` functions are trigger/event-trigger
  functions (not exposed by PostgREST; no application `SECURITY DEFINER` function exists). Caveat:
  the dry-run shows the migration is safe, but production only gets the explicit posture once
  `0003` is applied there — today it relies on Supabase's automatic policy-less RLS.
- **Security review sign-off — PARTIAL.** Technical evidence is complete (grant/deny matrix,
  probes, dry-run, tests); a named human reviewer still has to sign off at merge. Not a code defect.
- **RLS tested if enabled — PASS.** Static assertions (RLS flags, full verb matrix, explicit
  policies, default privileges) run in every environment; behavioural `SET ROLE` probes assert the
  app role can read/update and both client roles get `42501`, and are skipped only where the session
  cannot `SET ROLE` (Supabase `postgres`). CI repeats the static checks with psql.

## Issues found and fixed during validation

1. **The new suite ran `CREATE TABLE`/`DROP TABLE` against whatever `DATABASE_URL` pointed at**,
   including the production Supabase project loaded from `.env.local`. The probe is now gated to
   local hosts, and a read-only `pg_default_acl` assertion covers the default-privilege guarantee in
   every environment.
2. **CI asserted exactly 14 policies in `public`**, which would break the first time a later
   migration added a table (with its two required policies). Replaced with "exactly two policies
   for each of the seven E2-04 tables".
3. **ADR wording called the production RLS default "accidental".** Supabase's `rls_auto_enable`
   event trigger makes it automatic; corrected to "automatic / undocumented / untested".

## Post-review fixes

A read-only code review produced nine findings; all were applied (including the hardening and
backlog items). Finding 4's premise — that column-level ACLs survive `REVOKE ALL ON TABLE` — was
disproved empirically on PG16 (`attacl` is cleared and `has_column_privilege` returns false), but a
cheap `attacl` assertion was kept as defense-in-depth.

1. **Runbook could destroy data.** Step 2 now says to run only the read-only
   `tests/db-authorization.integration.test.ts` (or the two `SET ROLE` probes) against the project,
   and explicitly forbids `npm run test:db` there.
2. **Documented cutover broke the repo's own tooling.** `.env.example`/README/ADR now state that
   migrations, the seed, and `test:db` need the owner (`DATABASE_URL="$DIRECT_URL" npm run test:db`);
   `scripts/seed.mjs` and `scripts/migrate.mjs` refuse a `leavetrack_app` connection.
3. **The "every table ships RLS + both policies" rule was unenforced.** Added a global RLS check
   (all `public` tables except `schema_migrations`), per-table two-policy coverage, a column-ACL
   check, and a role-attribute check to both the test suite and CI.
4. **Deny policies were permissive.** Changed to `AS RESTRICTIVE`; a permissive deny would be OR'd
   away by a future permissive allow policy. Asserted in test + CI.
5. **Pre-existing role attributes were not normalized.** The migration now issues
   `NOBYPASSRLS/NOCREATEDB/NOCREATEROLE/NOREPLICATION` (and `NOSUPERUSER` only when the role is
   actually a superuser, since Supabase's `postgres` cannot alter that attribute) and the test
   asserts every flag.
6. **Function `EXECUTE` was left at PostgreSQL's default** (granted to `PUBLIC`). Revoked from
   `PUBLIC`/`anon`/`authenticated` for the three app functions, with default-privilege revokes for
   future functions. Triggers are unaffected (`EXECUTE` is checked at trigger-creation time).
7. **Default-privilege coverage was scoped to the migrating role.** Documented as residual risk,
   with RLS as the backstop for tables created by another role.
8. **`arch-summary.md` mirrored stale auth claims.** Corrected `ARCH-LeaveTrack-v1.0.md` (Stack +
   Open Questions) and regenerated the summary.
9. **Suite leaked the pool.** Added `afterAll(... end({ timeout: 5 }))` like every sibling suite.
