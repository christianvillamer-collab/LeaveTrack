## Acceptance criteria

- AC1 (US-01) — PASS: submitting a request writes an `in_app` row (status `sent`) and an `email`
  row (status `pending`) for the owner's manager in the same transaction as `leave_requests` and
  `audit_log`. `tests/notifications.integration.test.ts` asserts both rows, the recipient, and the
  reason in the body.
- Managerless fallback — PASS: with `manager_id is null`, every active `hr_admin` is enqueued, and
  `managerNotified` stays `false`, so the existing “HR review” copy remains accurate.
- AC2 (US-03) — PASS: approve, reject, and HR override each write two rows addressed to the request
  owner. The reject body carries the reason; the override body says `HR (Priya Nair) … as an
override`.
- Idempotency — PASS: the unique key `(event_type, leave_request_id, recipient_id, channel)` plus
  `on conflict do nothing` means a replayed decision (409) adds no second notification row.
- In-app inbox — PASS: `/notifications` lists only the session recipient's `in_app` rows; mark-read
  and mark-all-read are recipient-scoped in SQL, a foreign id is 404, and a second read is null.
- Email delivery — PASS: the worker delivers a pending row once and does not resend it; a failure
  is retried and succeeds on the next run; the attempt cap leaves a terminal `failed` row with no
  `next_attempt_at`; an unconfigured transport records `skipped` with no retry. The claim respects
  its batch cap exactly (`claimPendingEmails(3)` on six due rows returns three).
- Authorization — PASS: list/read routes require a session and take the recipient from it; the cron
  route is the only session-free path and requires the `CRON_SECRET` bearer token.
- DB policy — PASS: `tests/db-authorization.integration.test.ts` includes `notifications` with
  `SELECT/INSERT/UPDATE` allowed and `DELETE` denied for `leavetrack_app`, plus the client deny
  policy.

## Decisions recorded

- **Option A** (approved): a managerless submission notifies every active `hr_admin`; recipients are
  resolved in SQL and inactive users are skipped by the insert guard.
- **Option B** (approved): `EMAIL_TRANSPORT=log` is the default; `resend` is a dependency-free
  `fetch` adapter. A missing credential is terminal `skipped`, not an infinite retry.
- `runNotificationOutbox(transport?)` takes an injected transport so the integration tests exercise
  success, failure, and unconfigured behaviour without a provider call.
- `managerNotified` intentionally keeps its old meaning (`manager_id !== null`), despite the plan
  text; changing it would have altered the submit response contract.
- `in_app` rows are written as `sent`, not `pending`: they have nothing to deliver, and a pending
  in-app row would never be claimed by the email worker.

## Issues fixed during validation

- [FIX NOW] The initial `app-shell.tsx` rewrite was truncated mid-file and failed typecheck; it was
  restored in full with the unread prop.
- [FIX NOW] The integration test interpolated `decisionRow?.id`/`emailRow?.id` (possibly
  `undefined`) into `postgres.js` tagged templates, which both failed the typecheck and risked an
  invalid parameter. The ids are now captured as `?? ""` constants before use.
- [FIX NOW] `claimPendingEmails()` used `IN (select … limit n for update)`, which PostgreSQL
  re-evaluates per outer row: a 25-row cap processed the entire backlog (39 rows observed). The
  ordered, locked, limited set now lives in a `materialized` CTE; a regression test leases three of
  six due rows, and the other email tests park unrelated backlog rows so assertions are about one
  request. Both the ADR and `knowledge/patterns/notifications.md` record the guardrail.
