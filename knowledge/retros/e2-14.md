# E2-14 retro — 800-user HTTP load test

Status: implementation complete; live baseline pending an authorized run.

## What landed

- `scripts/load-test-800.mjs` is an HTTP-level harness: it seeds 8 managers, 1 HR
  admin, 800 employees, and 20,000 requests into a dedicated disposable
  database, provisions 809 confirmed Supabase Auth identities, links their
  subjects into `users.auth_subject`, and drives 800 signed-in virtual users
  against the running app.
- The workload mixes reads (`/balance`, `/requests`, `GET /api/leave-requests`,
  `GET /api/audit/:userId`) with a periodic `POST /api/leave-requests`, so the
  transactional submit path is exercised under concurrency.
- The harness records p50/p95/p99/max per endpoint plus success/failure counts,
  writes `docs/performance/e2-14-results.json`, and exits non-zero unless every
  p95 is under 500ms and there are zero request errors.
- `package.json` adds `load:800` and `load:800:seed`. No new dependencies.
- `.github/workflows/load-800.yml` runs weekly and on demand, gated by
  `E2_14_LOAD_TEST_ENABLED` plus four secrets, using a disposable Postgres service.
- `docs/performance/e2-14-load-test.md` is the run book; this task's ARCH line
  links to it.

## Decisions

- **HTTP, not DB-only.** E2-13 already proved the SQL is fast with one
  connection. E2-14 exists to prove the full authenticated request path holds
  at 800 users, so the harness authenticates for real and hits the Next server.
- **Fail closed, three layers.** Base URL, both DB URLs, and all auth secrets are
  validated before any network call; `current_database()` is asserted inside the
  seed transaction; the service role key is scoped to identity provisioning.
- **Dedicated database, no rollback.** Unlike E2-13's rolled-back benchmark, this
  harness commits to `leavetrack_e214_load`, a disposable local database that is
  never a Supabase project. Deterministic UUIDs keep reruns idempotent.
- **SSR cookie built to match the SDK.** The session cookie reproduces
  `@supabase/ssr`'s default `base64-` + base64url encoding and
  `sb-<ref>-auth-token` name, confirmed against the installed SDK source, so the
  proxy and Server Components accept it without a browser.
- **No new migration.** All columns, enums, and audit constraints the seed uses
  already exist in migrations 0001 and 0005.

## Validation notes

- `node --check` and ESLint pass on `scripts/load-test-800.mjs`.
- Schema assumptions were verified against source: `users.auth_subject` and its
  unique partial index (0005), `audit_log.action` allows
  `submitted|approved|rejected` (0001), and `leave_requests` request shape
  constraints match the seeded rows.
- Full gate (`lint → typecheck → test → build`) was run with `DATABASE_URL`
  unset to confirm the empty-environment build contract still holds.
- [FIX NOW — fixed] The first live run failed at seed time with
  `MAX_PARAMETERS_EXCEEDED`: postgres.js bound every cell of the 20,000-row
  request insert as a parameter, exceeding PostgreSQL's 65,534 limit. Bulk
  inserts are now chunked to 1,000 rows inside the same transaction, and the
  constraint is documented in `knowledge/patterns/load-testing.md`.
- [FIX NOW — fixed] The second live run seeded successfully but failed at sign-in
  with Supabase Auth `429 Request rate limit reached` after ~35 requests. Measured
  the same ~40-per-window per-IP limit on password grant, admin magic-link
  `verifyOtp`, and service-role-key requests. With user approval, the harness now
  mints a 32-session pool (8 managers + 1 HR + 23 employees), round-robins it
  across the 800 VUs by role, retries 429s with backoff, and records
  `authPoolSize` in the report. This is a deliberate deviation from the approved
  one-session-per-VU design; 800 concurrent authenticated requests and all
  measured endpoints are unchanged.

## Live run outcome

`npm run load:800` completed against the disposable database with 800 VUs and a
32-session pool. It **failed**: every endpoint's p95 sat at the 15s timeout and
2,558 requests failed. The honest JSON is committed as
`docs/performance/e2-14-results.json`; the run book records the numbers and the
layer-isolation probe. E2-14 stays Open — p95 < 500ms and zero errors were not
demonstrated, and no result was tuned to pass.

The probe isolated the cost: `/api/health` p95 102ms at 50 VUs,
`/api/leave-requests` 601ms, `/balance` 1452ms. Postgres itself is 1–7ms per
E2-13. The dominant layers are per-request Supabase Auth `getUser()` network
verification and SSR rendering, which saturate a single Next.js process at this
concurrency.
