# E2-13 retro — Server-side list pagination, filters, and index evidence

## What landed

- `lib/validation/list.ts` is the shared fail-closed contract for `status`, `page`, and `pageSize`
  (default 25, max 100). `lib/validation/audit.ts` adds `exportAll=1` and the E2-12 date bounds.
- `GET /api/leave-requests` and the `/requests`, `/approvals`, and `/audit` pages read one bounded
  page. Request ordering is `created_at desc, id desc`; audit ordering is `occurred_at desc, id desc`.
- Manager scope remains a SQL predicate (`e.manager_id = ${managerId}`). HR uses the separate
  `listOrgLeaveRequestsPage`; `scope=team` stays manager-only.
- `GET /api/audit/:userId?exportAll=1` returns the full employee/date/status filtered event set in
  the standard envelope. The client applies its local search/action filters before building the CSV,
  so the export still matches every matching row, not just the visible page.
- Status filters cast the parameter (`r.status = $1::request_status`), not the enum column, so the
  existing `request_status` indexes remain usable.
- `docs/performance/e2-13-baseline.md` records final p95/p99 and EXPLAIN evidence from a rolled-back
  800-user / 20,000-request dataset in `leavetrack_e207_verify`.

## Decisions

- **No new migration.** The three indexes named by E2-13 already exist in migration 0001 and EXPLAIN
  confirms they are used. Adding duplicate DDL would have been noise.
- **Fail closed, no silent fallback.** Invalid list or audit search params produce an explicit alert
  and no query; an API gets the standard 400 envelope. A malformed filter can never become an
  unbounded report.
- **One envelope, no new route.** `exportAll=1` reuses the existing audit route and success envelope.
  This keeps `withApiHandler` unchanged while avoiding a full-history payload on every page render.
- **Legacy array helpers kept.** `listMyLeaveRequests`, `listTeamLeaveRequests`,
  `listOrgLeaveRequests`, and the dashboard preview overload of `listAuditEventsForEmployee` still
  serve existing callers, so no broad call-site migration was needed.
- **Page-scoped summaries.** Status badges and approval summary cards are labelled as page-scoped
  instead of implying a full org/team aggregate that the 25-row query cannot support.

## Blast-radius notes

`graphify query` on the E2-13 symbols showed the new page helpers are called only by the intended
routes and pages (`GET /api/leave-requests`, `/requests`, `/approvals`, `/audit`) plus the shared
`rowPagination`/`toPaginationMeta` path. `DashboardPage`, `EmployeeDashboard`, `ManagerDashboard`,
and `HrDashboard` continue to use the legacy array helpers; no dashboard call site was changed.
The new `list.ts` community is referenced by `validation/leave.ts`, `validation/audit.ts`,
`lib/types.ts`, and `tests/list-pagination.test.ts`, which matches the approved plan. `.codegraph`
was not present, so the Codegraph blast-radius check was unavailable.

## Validation issues

- [FIX NOW — fixed] The first benchmark plan showed `r.status::text = $1`, preventing Postgres from
  using the `request_status` indexes. Filters now cast the parameter instead; the final EXPLAIN
  plans use `leave_requests_manager_scope_idx`, `users_manager_id_idx`,
  `leave_requests_status_created_idx`, and `audit_log_request_idx`.
- [FIX NOW — fixed] `count(*) over ()` returned as a string from postgres.js, so pagination metadata
  became zero. All window counts are now `::int`, and the DB integration tests pass.
- [FIX NOW — fixed] The benchmark harness initially miscounted pending rows (`g % 3` over 1..25
  yields 8, not `25 / 3`) and wrote nothing because a rollback sentinel was swallowed. The expected
  count and transaction control were corrected before the final run.
- [FIX NOW — fixed] Final benchmark numbers differed from the first recorded run; the baseline doc
  was reconciled with `e2-13-bench-final.json`.
- [FIX NOW — fixed] `count(*) over ()` has no row when OFFSET is past the end, so an out-of-range
  page reported `total: 0`. Each paged helper now falls back to a scalar `count(*)` built from the
  same postgres.js fragment, with integration tests for `/requests`-style scoped paging and audit.
- [FIX NOW — fixed] `/requests` and `/approvals` derived status counts from the current 25 rows but
  labelled them org/team-wide. The badges and cards are now explicitly page-scoped; org-wide counts
  would need dedicated SQL aggregates.

## Backlog items

- [BACKLOG] `getAuditReport` still loads the full filtered `requests` array for the summary cards
  (`Requests`, `Decisions`, `Pending`). The paginated list is the event timeline; a future task can
  replace the request array with SQL aggregate counts if long histories become a latency issue.
- [BACKLOG] `app/api/leave-requests/route.ts` and `app/api/audit/[userId]/route.ts` use
  `searchParams.get()`, so repeated query keys collapse to the first value on APIs. Page props still
  reject arrays. If strict API rejection is required later, use `getAll()` and pass arrays to the
  shared schema.
- [BACKLOG] Inherited from E2-12 review: `docs/arch-docs/ADR-LeaveTrack-E2-12-Audit-Export.md` still
  says the page falls back to defaults and that pagination is a display slice. E2-13 supersedes both
  statements; this ADR belongs to the open E2-12 PR and was intentionally not edited here.
- [BACKLOG] Inherited from E2-12 review: the UTC date-bound expression was flagged as
  session-timezone-dependent. No change was made in E2-13.
- [BACKLOG] `app/(app)/approvals/page.tsx` can show pending and decided rows on one page but attaches
  pagination controls to only one table. A single shared nav below both sections would be clearer.
- [BACKLOG] The p95 evidence is a database-only, single-connection baseline. E2-14 covers the HTTP
  p95/p99 at target load; the E2-13 AC was accepted on this DB-level evidence.
- [BACKLOG] `docs/dev-tasks/epic-2-production-readiness-tasks.csv` still marks E2-13 as `Open`; it is
