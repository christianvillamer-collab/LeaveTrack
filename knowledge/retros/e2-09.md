## Acceptance criteria

- AC1 — PASS: reassigning a person updates `users.manager_id`, and the manager queue joins on that
  column, so pending requests move to the new manager without any request rewrite.
  `tests/people-admin.integration.test.ts` now creates a pending request, reassigns its owner, and
  asserts it leaves the previous manager's queue and appears in the new one, still `pending`.
- AC2 — PASS: `reassignManager` rejects self, inactive/non-manager candidates, and any assignment
  that closes a reporting cycle (recursive CTE with `union`), serialized by
  `pg_advisory_xact_lock(hashtext('users.manager_graph'))`. Cycle rejection writes no audit row.
- AC3 — PASS: `getSession` returns `null` for an inactive row (unit-covered in
  `tests/auth-session.test.ts`), and both the login action and `/auth/callback` sign the provider
  session out and surface a deactivated message.
- AC4 — PASS: profile edits, manager reassignment, deactivation, reactivation, and import changes
  each write exactly one `user_audit_log` row in the same transaction; no-op saves write none.
  Covered per action in the people-admin integration suite.
- AC5 — PASS: bulk import is all-or-nothing, keyed on `lower(email)`, skips identical rows without
  an audit row, ignores role changes on existing rows, and rolls the whole batch back on one bad
  row.
- Safe paths — PASS: HR edits name/email/job title/team, reassigns managers, deactivates/reactivates,
  and imports up to 200 rows per request. Sign-in identity follows `auth_subject`, with the verified
  email only as an unlinked-row fallback; unlinked rows cannot have their email edited (409).

  row (`{"name":…,"email":…,"team":"Design"}`) cleared `manager_id` and pulled pending requests out
  of the manager queue. The import contract is now three-state end to end — Zod keeps `undefined`
  distinct from `null`, the route forwards it, and the `update` uses `case when <provided>` per
  column. New regression tests cover omitted-keeps and null-clears in both validation and DB layers.
- [FIX NOW] The import JSDoc and the import-form hint claimed HR could link a provider account
  later; no such action exists. Both now say the subject binds on the first sign-in with the
  matching verified email, or via `npm run auth:seed` in development.

## Environment note

`scripts/migrate.mjs` and `scripts/seed.mjs` prefer `DIRECT_URL` over `DATABASE_URL`. The first
validation migration run therefore applied `0003`, `0004`, and `0005` and re-ran the idempotent seed
against the Supabase project configured in `.env.local`, not the local Docker database. The
migrations are forward-only and the seed is `on conflict do nothing` throughout. Local DB
verification then overrode **both** URLs and rebuilt the disposable database from scratch.
